## 2. WAD format contract

All format integer fields are **little-endian signed 32-bit** values as consumed by classic Doom. Use explicit decoding and 64-bit intermediates for bounds. File contents are untrusted; do not overlay native PureBasic structures over bytes from the file.

### Header (exactly 12 bytes)

| Offset | Size | Meaning |
|---:|---:|---|
| `0x00` | 4 | Exact magic `IWAD` or `PWAD` |
| `0x04` | 4 | Number of directory entries (`int32`, nonnegative) |
| `0x08` | 4 | Byte offset of directory (`int32`, normally nonnegative) |

### Directory entry (exactly 16 bytes per lump)

| Relative offset | Size | Meaning |
|---:|---:|---|
| `0x00` | 4 | Position of lump payload (`int32`) |
| `0x04` | 4 | Payload length (`int32`) |
| `0x08` | 8 | Raw 8-byte lump name; may have **no terminating NUL** |

**Important compatibility points:**

- The directory offset in the header is authoritative; the directory is **not necessarily at EOF**.
- Entries are in directory order, **not necessarily sorted by payload offsets**. Data blocks may overlap or share the same offset.
- Zero-length entries are valid markers (e.g. `F_START`); their recorded payload position may be meaningless, including outside the file. **Never seek to / read a zero-length marker position**. Do not reject a WAD solely because its zero-length marker's position is outside the file.
- Names are 8 raw bytes. Handle NUL padding and exact 8-character names, keeping the original byte representation available. Avoid over-validating non-ASCII or unusual names at this stage; names are metadata, never file paths.
- Do not hash a WAD to decide whether its container format is valid. Recognizing particular game editions by MD5 is a **later** concern.
- For an empty directory (`count=0`), accept a structurally valid 12-byte WAD without allocating entries or dereferencing an absent directory. Define and test a reasonable convention for its unused directory offset.

## 3. Implementation requirements

### 3.1. Modules and API

Create only the modules needed, following the existing project layout. Suggested locations:

- `src/Core/Endian.pbi` — tested decoding of little-endian 16/32-bit values as needed; do not import platform-specific types.
- `src/WAD/WAD.pbi` — header/directory structures, parser lifecycle, error reporting and safe cleanup.
- `src/DoomPB.pb` — minimal integration with existing CLI, without breaking M0 commands.
- `tests/unit/...` — self-contained tests that use **synthetic** WAD files generated by test code.
- `scripts/test.ps1` and (where safe) `scripts/test.sh` — run the new test executable(s) alongside existing smoke checks. Preserve script behavior when invoked outside repo root.
- `docs/PORTING_NOTES.md` — record mapping from upstream C symbols, confirmed assumptions, intentionally stricter malformed-file behavior.

Treat these as suggested file locations, **not** an instruction to create empty placeholder modules. Match the actual project architecture, and avoid circular `XIncludeFile` dependencies.

Provide a small, documented, reusable API that can later support multiple WAD files and lookup overlays. Suggested operations (names may be adapted):

1. Open a specified WAD path, validate and read the header and directory into owned memory.
2. Return type (`IWAD`/`PWAD`), file size and directory-entry count.
3. Inspect an entry **by index**, including byte offset, length, raw name and a safe display name.
4. Close/release all resources; reinitialization and repeated open/close must be safe.
5. Report errors with actionable text; no silent fallbacks or partial 'success' state.

Do **not** implement by-name lookup or payload loading yet (M1-02). Internal data should make both straightforward to add.

### 3.2. Safety and numeric semantics

- Check that input is at least 12 bytes before parsing the header. Require only exact `IWAD` or `PWAD` signatures.
- Reject negative directory count or negative directory offset (except where the offset is unused for a zero-entry file, as explicitly documented).
- Calculate `directory_size = Int64(count) * 16` and `directory_end = Int64(directory_offset) + directory_size` **before** allocation or seeking. Reject truncation/out-of-file ranges and allocation sizes not representable in the host runtime. Impose a documented allocation limit only if needed; do not reject legitimate WADs arbitrarily.
- For every **nonempty** entry, reject negative position/size and ensure `Int64(position) + Int64(size) <= file_size`. Offset equal to `file_size` is valid only when size is zero.
- For zero-length entries, record the raw offset, but **do not validate it as a dereferenceable data range**. Never read at that offset.
- Distinguish signed values used by the original C code from unsigned bytes used by the parser. Verify the PureBasic syntax and conversions with the real 6.41 compiler.
- Detect short reads explicitly, with checks on `ReadData()` return values; `FileSeek()` position must only be used after validation. `Lof()` provides a 64-bit length.
- Do not read a whole user WAD into RAM merely to parse its directory. Keep memory consumption proportional to the directory.
- Define ownership of allocated buffers and files for every success and failure path; no double-free, leaks or stale global parser state.
- A malformed WAD must lead to a controlled error, **not** out-of-bounds memory access, crash, hang, or huge allocation.
